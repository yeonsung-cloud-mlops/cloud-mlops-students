# 클라우드 MLOps 팀빌딩 학생 장표 콘텐츠

배치: 1주차, 과목 소개와 AWS 실습 사이  
운영 시간: 팀 구성 55분 + 주제 선택 45분 + 다른 팀 공격 검토 40분
학생 결과물: 개인 역량 여권, 팀 협상판, 팀 등록표, 팀 규칙, 역할 순환표, 주제 후보 비교표, 공격 검토표, 프로젝트 후보 카드

> 실제 활동 순서와 33장 구성은 `학생주도_팀빌딩_주제선정_활동교안.md`를 우선 적용한다. 아래 13장은 개념 설명과 요약 장표로 사용한다.

---

## 장표 1 — 이 과목은 팀이 하나의 서비스를 완성하는 수업입니다

- 15주 뒤 결과: 다른 사람이 링크로 접속해 사용할 수 있는 ML 서비스
- 팀이 함께 할 일: 문제 정의, 데이터, 모델, API, AWS 배포, 모니터링, 발표
- 오늘 할 일: 팀을 정하고 “어떻게 함께 일할지”를 파일로 남기기

> 발표자 노트: 절대 완성된 모델을 가져오는 수업이 아니다. 모델을 만들어 배포하고 운영하는 전 과정을 팀이 차례로 경험한다.

## 장표 2 — 4명이 한 팀이고, 남는 인원은 3명 팀으로 구성합니다

- 권장: 4명
- 허용: 전체 인원이 나누어지지 않으면 3명 팀
- 금지: 2명 팀, 5명 이상 팀, 친한 사람만 먼저 확정하기
- 구성 조건: Python이 덜 낯선 사람, 문서·발표에 자신 있는 사람, AWS·서버를 배워 보고 싶은 사람이 한쪽에 몰리지 않게 구성

팀을 못 정한 학생은 수업이 시작된 뒤 15분에 강사가 배정한다.

## 장표 3 — 실력을 자랑하는 대신 지금의 상태를 표시하세요

각자 아래 4개 항목에 `좀 해봤다 / 처음이지만 배워 보고 싶다`를 표시한다.

1. Python·데이터
2. 화면·API 개발
3. Linux·AWS·Docker
4. 문서·발표·일정 관리

팀 구성은 “잘하는 사람”을 모으는 활동이 아니라, 서로 다른 경험을 섞는 활동이다.

## 장표 4 — 7분 동안 서로의 일하는 방식을 확인하세요

한 사람당 45초로 아래를 말한다.

- 이 수업에서 반드시 해 보고 싶은 것 1개
- 지금 가장 부담스러운 것 1개
- 팀에 기여할 수 있는 것 1개
- 미리 알려야 하는 일정·접근성 사항 1개

질문이 끝나면 지금 팀을 유지할지, 다른 구성을 찾을지 결정한다.

## 장표 5 — 역할은 서열이 아니라 이번 단계의 책임입니다

| 역할 | 이번 단계에서 책임질 것 |
|---|---|
| 제품·데이터 | 문제 정의, 데이터 카드, 사용자 화면 |
| 모델·실험 | 베이스라인, 지표, MLflow 실험 비교 |
| 플랫폼·배포 | Docker, ECR, EC2, GitHub Actions |
| 운영·품질 | 테스트, CloudWatch, README, 발표 증거 |

- 3명 팀은 `운영·품질`을 다른 역할과 함께 담당한다.
- 팀장은 상시 역할이 아니다. 일정 조정과 의사소통 창구만 담당한다.
- 역할은 4주차, 8주차, 12주차 종료 후에 순환한다.

## 장표 6 — 모든 학생이 코드를 남기고 시연을 합니다

개인별 최소 증거:

- 각 마일스톤에서 본인 커밋 1개 이상
- 15주 동안 발표·시연 1회 이상
- 다른 사람이 만든 기능에 대한 리뷰·테스트 1회 이상
- 자신이 해결한 문제를 `증상 → 원인 → 조치 → 결과`로 1건 이상 기록

“잘하는 한 명이 대신 했다”는 팀 완성으로 인정하지 않는다.

## 장표 7 — 팀 규칙은 네 문장으로 정합니다

`TEAM_CHARTER.md`에 네 가지를 작성한다.

1. 언제까지 답장할까? — 예: 평일 24시간, 마감 당일 2시간
2. 결정은 어떻게 할까? — 예: 10분 논의 후 과반수, 동률은 담당자 결정
3. 못 할 때는 언제 알릴까? — 예: 마감 24시간 전
4. 충돌이 생기면 어떻게 할까? — 예: 당사자 대화 → 팀 논의 → 교수자 조정

계정 비밀번호·AWS 액세스 키를 메신저나 Git에 올리지 않는다.

## 장표 8 — 팀 프로젝트는 “데이터로 답할 수 있는 질문”으로 시작합니다

오늘은 `실습프로젝트_예시주제_학생가이드.md`의 8개 후보 중 2개를 정한다. 3주차에 데이터를 직접 받아 확인한 뒤 1개를 최종 확정한다.

우선 추천은 `서울 자전거 대여량`, `건물 난방·냉방 부하`, `설비 고장 가능성` 예측이다.

- 누가 쓰는가?
- 무엇을 입력하는가?
- 무엇을 예측·분류하는가?
- 결과를 어떤 화면에서 보여줄까?
- 성공을 어떤 숫자로 확인할까?

사람을 평가하거나 채용·신용·질병 같이 고위험 결정을 자동화하는 주제는 선택하지 않는다.

## 장표 9 — 팀 파일은 여기서 받습니다

- LMS: `1주차 → 팀빌딩 자료`
- 파일: `cloud-mlops-team-start-kit-v1.zip`
- 압축 해제 위치: `~/cloud-mlops/team-project/`
- 제출: `TEAM_REGISTRATION.md`, `TEAM_CHARTER.md`, `ROLE_ROTATION.csv`, `PROJECT_IDEA_CARD.md`

```bash
mkdir -p ~/cloud-mlops/team-project
cd ~/cloud-mlops/team-project
unzip -q ~/Downloads/cloud-mlops-team-start-kit-v1.zip
cd team-start-kit
bash verify.sh
```

정상 출력: `READY: team-start-kit`

## 장표 10 — 이름이 아니라 팀의 작업 공간을 만듭니다

팀 이름은 영문 소문자·숫자·하이픈만 사용한다.

```text
좋은 예: team-river, blue-owl, mlops-03
피할 예: Team 1, 1조최고, 한글과 공백이 있는 이름
```

이 이름을 다음 곳에 같게 사용한다.

- GitHub 저장소: `cloud-mlops-<team-name>`
- AWS 태그: `Project=cloud-mlops`, `Team=<team-name>`, `Owner=<student-id>`
- S3·ECR 리소스 접두어: `mlops-<team-name>-...`

버킷 이름은 전 세계에서 중복될 수 있으므로 실제 생성 전에 확인한다.

## 장표 11 — 활동이 끝나면 여섯 개 파일을 팀 대표가 제출합니다

제출 전 확인:

- [ ] 팀원 전원의 학번·이름이 있다.
- [ ] 다음 4주의 역할이 중복 없이 배정됐다.
- [ ] 답장·결정·일정 공유·충돌 해결 규칙을 적었다.
- [ ] 프로젝트 후보에 사용자·입력·결과가 있다.
- [ ] 팀 구성 협상판과 주제 후보 독립 채점표가 있다.
- [ ] 팀원 모두가 파일 내용을 읽고 동의했다.

제출 위치: LMS `1주차 → 팀 등록`  
제출 주체: 팀 대표 1명  
제출 후: 팀원 전원이 제출 파일을 다시 확인

## 장표 12 — 결석·이탈·충돌은 숨기지 말고 기록하면 해결할 수 있습니다

- 오늘 결석: 강사가 임시 배정하고, 다음 수업 시작 10분 내에 팀 재확인
- 2회 연속 무응답: 팀이 기록한 후 강사에게 알림
- 역할 편중: 커밋·시연·리뷰 기록으로 확인하고 다음 단계에서 역할 재배치
- 중도 이탈: 기존 팀원의 남은 역할을 재배치하고, 2명이 남으면 강사가 팀 통합 결정
- 충돌: 사람 평가 대신 `마감·파일·작업` 사실을 기록해 조정 요청

## 장표 13 — 오늘 팀빌딩은 네 가지를 완료하면 끝납니다

1. 나의 현재 경험과 배우고 싶은 영역을 공유했다.
2. 3~4명으로 팀을 구성했다.
3. 역할 순환표와 팀 규칙을 작성했다.
4. 프로젝트 후보 카드와 팀 등록표를 제출했다.

다음 주: 자신의 역할로 Linux·EC2 환경을 준비한다.
